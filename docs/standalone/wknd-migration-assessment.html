Executive Summary purpose, objectives, scope

Purpose of the site

WKND is Adobe's reference travel & adventure brand — an editorial + listings site (adventures, magazine articles, FAQs, contributor profiles). It is a template-driven AEM Sites site (Core Components, Experience Fragments, DAM assets) with no transactional or personalization dependencies.

Migration objectives

  • Move WKND onto Edge Delivery Services with content authored in Document Authoring (da.live).
  • Reach PageSpeed 100 (Core Web Vitals) on mobile & desktop.
  • Deliver a lean, reusable block library — reuse over custom, config over code.
  • Make listings self-maintaining (query-index-driven) so content ops need no developer.

Scope of migration

64 pages analyzed → 27 US/EN + CA/EN pages migrated across 6 templates, delivered with 13 EDS blocks + global header/footer. Nine minor-locale "coming soon" stubs deferred. Result: 100% of in-scope pages live, 0 open defects.

Migration Approach execution

The migration was executed as a repeatable, template-driven pipeline rather than page-by-page hand-conversion. One template is fully solved end-to-end, its parser/transformer set is proven, then the same engine is replayed over every URL in that template. This is what makes 27 pages (and later, the whole locale tree) reproducible and auditable.

How the engine works (steps 5–7 in detail)

Each import-<template>.js is self-contained: it registers the template's parsers and the shared transformers, embeds the template config, then runs every URL through the same sequence.

Parser — per block

Turns a source component's DOM into an EDS block table (row 1 = block name, following rows = cells). Every field is treated as optional so one parser serves structural variants.

Example — hero-banner: a single parser serves both the homepage teaser (image + heading + optional CTA) and the adventure-detail mini-carousel (image only). It probes several selectors (.cmp-teaser__image img, .cmp-carousel__item--active img, …) and emits only the rows that exist.

Transformers — per page

wknd-cleanup.js strips AEM chrome (header/footer/instrumentation, empty wrappers, tracking); wknd-sections.js then inserts the section boundaries EDS uses. They run in order, site-wide — the same two on every template — so page structure is consistent.

Worked example — adventure-detail (16 pages imported)

The import registers hero-banner + table-facts parsers and the two transformers, then replays over urls-adventure-detail.txt (16 US/EN pages; the 16 CA/EN equivalents reuse the same set). Per page: hero image → hero-banner; the AEM fact sheet (Activity, Trip Length, Difficulty, Price…) → table-facts; tabbed body (Overview/Itinerary/What to Bring) flattened to headed default content; a .report.json records what was emitted. One parser set, identical runs per page.

Auto-blocking

Auto-blocking creates blocks that authors never explicitly place — buildAutoBlocks() in scripts.js runs during eager page decoration and turns content patterns into blocks automatically. This project uses two auto-blockers, so authors just paste a link and the right block appears.

Auto-blockTriggerBehavior
FragmentA link whose href contains /fragments/ (not already inside a .fragment)Loads the fragment via loadFragment() and replaces the link with its content — reusable content (e.g. shared promos) without authoring a block
WidgetA link whose href contains /widgets/Wraps the link in a widget block (via buildBlock); a standalone link-in-paragraph is replaced by the block, otherwise the link is swapped in place
Why it matters

Auto-blocking keeps authoring simple: no table markup for fragments or widgets — a plain link is enough. It runs inside the eager phase and fails safe (wrapped in try/catch), so a bad reference logs an error rather than breaking the page. The global header and footer are loaded by the same fragment mechanism.

Guiding principles

  • Template-first, highest-volume-first — solve adventure-detail (largest template) first; one parser set covers ~half the migrated pages and de-risks the rest.
  • One parser, many variants — parsers are defensive (all fields optional) so a single file serves structural variants across templates.
  • Shared transformers — cleanup + sectioning run identically on every page, so structure never drifts between templates.
  • Reuse over custom — every block derives from a Block Collection base; no bespoke one-off blocks.
  • Config over code — listings are sheet/index-driven (see Dynamic Rendering), so new content needs no developer.
  • Verify before publish — preview → in-browser validation against source → publish; nothing goes live unverified.
